# 09 · 延迟优化方案

> 产出日期：2026-10-20
> 适用版本：`follow.py` / `detect.py` / `camera.py`（commit `c4ee545` 及之前）
> 目标：把「眼睛能感觉到的延迟」从 **~370 ms** 压到 **~80 ms**
> 原则：**先测后改**。第 1 节对齐事实，第 2 节给出模型，第 3 节才是改动。

---

## 0 · 一句话结论

> **推理只占总延迟的不到 8%。延迟的 60% 在控制侧的两个常数上。**

`follow.py` 里的 `SMOOTH = 0.25` 和 `MOVE_MS = 200`，两个数贡献了约 **300 ms**；
而 YOLO 推理只有 **27 ms**。

**先改参数，再谈模型。** 顺序反了，会花两天时间优化一个只占 8% 的环节。

## 2 · 延迟模型

### 2.1 公式

目标匀速移动时，各环节的等效滞后**近似可加**：

```
D ≈ T/2  +  E/2  +  P  +  τ  +  ms  +  2 ms
    相机    曝光   处理   滤波   舵机   总线
```

| 符号 | 含义 | 来源 |
|---|---|---|
| `T` | 帧周期 = 1/fps | 相机配置 |
| `E` | 曝光时长 | 自动曝光决定，**需实测** |
| `P` | 预处理 + 推理 + 后处理 | `detect_frame` 的返回值 + rotate |
| `τ` | 指数滤波时间常数 | 由 `SMOOTH` 和 `T` 算出 |
| `ms` | 舵机定时运动时长 | 串口命令里的第三个参数 |

> 这些项不是严格的纯延迟，而是各环节的**稳态滞后**；对匀速目标，一阶环节的滞后可以线性相加。数量级参考足够。

### 2.2 τ 怎么算

`pan += (target − pan) × α` 是标准的一阶低通：

```
τ = −T / ln(1 − α)
```

代入 `T = 33.3 ms`（30 fps）、`α = 0.25`：

```
τ = −33.3 / ln(0.75) = 33.3 / 0.2877 ≈ 116 ms
```

**到 90% 需要 2.3τ ≈ 265 ms。** 这是一个比推理大 4 倍的数量级。

> 注意：`α` 是「每帧」的系数。帧率一变，`τ` 就变。
> 这也是 Step 1 要把滤波改成按 `dt` 计算的原因——否则上 60 fps 后行为会悄悄改变。

### 2.3 舵机的物理上限

LX-16A 空载约 **0.16 s / 60°**，量程 1000 编码 = 240°：

```
1 编码 = 0.24°
当前安全限位 400~600 = 48° → 物理行程约 130 ms
```

- **跟随中的小步长**（每帧几编码 ≈ 1~2°）用 `ms=50` 绰绰有余，不会被物理限速；
- **刚锁到人时的大跳变**物理上就是 100 ms 级别，这是机械能力，**改参数也改不掉**。

### 2.4 代入现在的参数

| 项 | 值 | 说明 |
|---|---|---|
| `T/2` | 16.7 ms | 平均等下一帧 |
| `E/2` | ~7.5 ms | 假设曝光 15 ms（**待实测**） |
| `P` | 29.6 ms | 27 ms 推理 + 2.5 ms 全帧 rotate |
| `τ` | **116 ms** | 由 α=0.25 算出 |
| `ms` | **200 ms** | 舵机行程参数 |
| 总线 | 2 ms | 115200 下 12 字节 |
| **合计** | **≈ 372 ms** | |

### Step 1 · 控制参数（1 小时，收益最大）

**改动只有三行，但这是 ~372 ms → ~135 ms 的那一步。**

#### 改动 1：`MOVE_MS: 200 → 50`

```python
MOVE_MS = 50        # 原 200
```

这个参数不是「平滑度」，是**速率限制**：舵机以 `delta / ms` 的速度走。
目标匀速移动时，稳态滞后 = **速度 × ms**。改成 50 直接砍掉 150 ms。

#### 改动 2：`SMOOTH` 改成时间常数

```python
TAU = 0.030         # 目标时间常数 30ms，替代 SMOOTH=0.25

# 每帧：
alpha = 1.0 - math.exp(-dt / TAU)
self.pan += (target - self.pan) * alpha
```

`dt` 是本帧实际耗时。这样帧率从 30 变到 60，滤波强度不变，行为可预测。

#### 改动 3：加死区

```python
DEADBAND = 4        # 4/1000 ≈ 0.96°

if abs(target - self.pan) < DEADBAND:
    target = self.pan
```

把 `τ` 从 116 ms 压到 30 ms，代价是舵机会跟着检测框的几像素抖动而轻微抖。
**死区的意思是「误差小于 1° 就当没误差」——有了它才敢把 τ 调小。这两个必须一起改。**

#### 完整替换：`follow.py` 的 `step()`

```python
    def step(self, verbose=False):
        t0 = time.perf_counter()
        dt = max(t0 - self.t_prev, 1e-3)
        self.t_prev = t0

        ok, frame = self.cap.read()
        if not ok:
            return None
        # 不再 rotate —— 只用 cx，180° 翻转等价于 offset 取负（见 Step 2）

        dets, _ = detect_frame(self.model, frame, conf=CONF)
        person = self.biggest_person(dets)
        self.frames += 1

        if person:
            self.hits += 1
            x1, y1, x2, y2 = person["box"]
            cx = (x1 + x2) / 2.0
            offset = max(-1.0, min(1.0, (cx - W / 2.0) / (W / 2.0)))
            if self.flip:
                offset = -offset
            target = PAN_CENTER + offset * (PAN_MAX - PAN_MIN) / 2.0
        else:
            target = PAN_CENTER

        if abs(target - self.pan) < DEADBAND:
            target = self.pan

        alpha = 1.0 - math.exp(-dt / TAU)
        self.pan += (target - self.pan) * alpha
        self.send_move(self.pan)

        if verbose:
            print("  舵机=%3.0f (%.1fms)" % (self.pan, dt * 1000))
        return {"person": bool(person), "pan": self.pan}
```

配套：

- `__init__` 里加 `self.t_prev = time.perf_counter()`
- 文件头 `import time` 已有，补 `import math`
- **没人时回中那一行**（`follow.py:131`）的 `400` 也改成 `MOVE_MS`

#### 预期与验证

| | 改前 | 改后 |
|---|---|---|
| `τ` | 116 ms | 30 ms |
| `ms` | 200 ms | 50 ms |
| 等效延迟 | ~372 ms | **~135 ms** |

**验证**：`loop` 的 p50 基本不变（还是 27~33 ms），但**体感明显变快**。
这本身就是证据：延迟不在循环里。

#### 反作用

舵机可能轻微抖动。先调 `DEADBAND`（4 → 6），不要急着把 `TAU` 调回去。

### Step 2 · 相机管线（半天）

#### 改动 1：删掉每帧的 180° 旋转

```python
# 删除这两行（follow.py:109-110）
if self.flip:
    frame = cv2.rotate(frame, cv2.ROTATE_180)
```

**为什么可以直接删**：

> 180° 旋转对 x 坐标的作用是 `x → W−1−x`，所以 `cx → W−cx`，即 `offset → −offset`；
> 垂直翻转只影响 y，而这里只用水平分量。
> 因此旋转是纯冗余，删掉后把 `offset` 取负即可，**数学上完全等价**。

省掉每帧一次 2.8 MB 的内存读写。

> ⚠️ **二选一**：如果改成删 rotate + 取负，就**不要**再在 GStreamer 里加 `flip-method=2`，否则会翻两次。
> 以后加俯仰舵机需要 y 时，再切回 `flip-method=2` 并把取负去掉。

#### 改动 2：相机 30 → 60 fps，卡死曝光

```python
W, H = 1280, 720
FPS = 60              # 原 30

pipeline = (
    "nvarguscamerasrc sensor-id=0 aeantibanding=2"
    " exposuretimerange=\"1000 8000000\" gainrange=\"1 16\""
    " ! video/x-raw(memory:NVMM),width=%d,height=%d,framerate=%d/1,format=NV12"
    " ! nvvidconv"
    " ! video/x-raw,format=BGRx ! videoconvert"
    " ! video/x-raw,format=BGR ! appsink drop=1 max-buffers=1 sync=false"
    % (W, H, FPS)
)
```

| 改动 | 省下 | 说明 |
|---|---|---|
| `framerate 30 → 60` | ~8 ms | IMX219 720p 支持 60 fps。而且 **τ 随 T 减半** |
| `exposuretimerange` 上限 8 ms | 最多 25 ms | 单位 ns。自动曝光在暗处会拉满一帧，这是最隐蔽的延迟源 |
| `gainrange="1 16"` | — | 曝光压短后靠增益补亮度 |
| `max-buffers 2 → 1` | 最多 16 ms | `drop=1` 下最多还能积压 1 帧 |
| `sync=false` | — | 不跟管线时钟走，帧一到就交 |
| 删 rotate | 2.5 ms | 见改动 1 |

> `exposuretimerange` 的具体数值要按现场亮度微调。**卡太死会噪点变多**——但 YOLO 对这种噪声不敏感，可以先卡 8 ms 试。

#### 同步改 `camera.py`

`detect.py camera` 用的是 [camera.py:107](../jetson/camera.py#L107) 的 `frames()`，是**另一条独立管线**，要一起改，否则两个脚本的实测结果对不上。

#### 预期与验证

`grab` 的 p50 应从 ~16.7 ms 降到 ~8 ms，`loop` 周期应稳定在 17~20 ms。
用 `v4l2-ctl --stream-mmap --stream-count=300` 或 appsink 计数确认相机真的跑了 60 fps。

### Step 3 · 预处理与模型输入（1 天）

#### 现状

现在把一张 16:9 的图塞进 640×640 的方框，**右边一大块是灰边填充，约 44% 的算力在算灰条**。

#### 改动 1：按真实宽高比导出

```python

YOLO("yolov8n.pt").export(
    format="engine",
```

> `imgsz` 接受元组是 ultralytics 8.3.x 的行为，以你板子上的版本为准；报错就退回 640。

#### 改动 2：把 engine 接进来

```python
# detect.py:22
MODEL = "yolov8n.engine"

def load(model_path=MODEL):
    from ultralytics import YOLO
    if not os.path.exists(model_path):
        print("[detect] 找不到 %s，回退到 yolov8n.pt" % model_path)

```

> 用 **ultralytics 自己的 export** 导出的 engine 带类别名元数据；
> 如果用裸 `trtexec` 转换，类别名会变成 `class0/class5`，需要手动映射（见 07-踩坑记录）。
> engine 加载依赖 `tensorrt` + `pycuda`；PyCUDA 没装时先 `pip3 install pycuda`。

#### 改动 3：GStreamer 先缩到模型输入尺寸

让 GPU 做缩放，CPU 就不用搬 1280×720 的整帧：

```
... ! nvvidconv flip-method=0
    ! video/x-raw(memory:NVMM),width=640,height=384,format=NV12
    ! nvvidconv
    ! video/x-raw,format=BGRx ! videoconvert
    ! video/x-raw,format=BGR ! appsink drop=1 max-buffers=1 sync=false
```

CPU 每帧要处理的数据从 **3.7 MB → 0.98 MB**。

#### 改动 4（可选，价值在简历上）

绕开 ultralytics 的 Python 预处理，自己写一个 CUDA 核，把 BGR → RGB float CHW 直接写进 TensorRT 的 binding。
这是「真正做过部署」和「只会调库」的分界线。

#### 预期与验证

`infer` 的 p50 应从 ~27 ms 降到 ~14 ms。
用 `model.val()` 在同一个验证集上对比 mAP，确认换分辨率后精度没掉。

#### 反作用

分辨率降低后，**远处的小目标可能漏检**。
验证方法：让目标在 3~4 m 处走动，比较 640×640 与 640×384 的检出率。掉得多就退到 640×480。

### Step 4 · 前馈（半天）

到这一步，剩下的主要滞后是滤波的 30 ms 和舵机行程的 50 ms。
**前馈能把滤波滞后直接买回来。**

```python
# 目标速度估计（一阶差分 + 低通，低通是必须的）
raw_v = (target - self.target_prev) / dt
self.v = 0.75 * self.v + 0.25 * raw_v
self.target_prev = target

# 提前量
LEAD = TAU                      # 先只用 30ms；想更快可以改成 TAU + MOVE_MS/1000
lead = target + self.v * LEAD
lead = max(PAN_MIN, min(PAN_MAX, lead))    # 必须限幅

alpha = 1.0 - math.exp(-dt / TAU)
self.pan += (lead - self.pan) * alpha
```

**道理**：滤波是「用滞后换平稳」，前馈是「用预测把滞后买回来」。
目标匀速移动时，稳态误差接近零——**舵机不再落后于人**。

> 风险点：速度估计会被检测框抖动放大。`0.75/0.25` 的低通不能省。
> `lead` 必须 `clamp`，否则目标突然消失时舵机会冲出去。

## 5 · 明确不做的事

| 不做 | 原因 |
|---|---|
| **采集/推理解耦（开线程）** | 推理（12~27 ms）小于帧周期（16.7~33 ms），线程化**不会减少任何延迟**，只会在处理超时时防止堆积。当前参数下收益 ≈ 0 |
| 换更大的模型 | YOLOv8s 只有 ~15 FPS，和「降延迟」方向相反 |
| 上完整 PID | 单目标跟随，一阶滤波 + 前馈足够；多出来的参数只会更难调 |
| 降低 `conf` 阈值 | 会引入假阳性，是拿精度换速度，和本方案目标冲突 |
| CUDA 手写检测后处理 | 收益 < 2 ms，投入产出比太低（但 Step 3 的 CUDA 预处理值得做） |

## 7 · 附：报告指标的推荐口径

面试官最容易追问的一句话是「**你这个延迟是怎么测的**」。
建议把 6.2 的表改成「数值 + 口径」两列：

| 指标 | 数值 | 测量口径 |
|---|---|---|
| 相机帧率 | 60.0 fps | appsink 计数 / 10 s |
| 纯推理延迟 | X ms | `trtexec --avgRuns=200` |
| 前后处理开销 | Y ms | ultralytics 计时 − 纯推理 |
| **相机 → 指令延迟** | X ms（p95 = Y） | 打点：`read()` 返回 → 串口写完成 |
| **指令 → 到位延迟** | Z ms | 阶跃响应 / 慢动作 |
| **物理端到端** | X+Z ms | 手机 240 fps 慢动作交叉验证 |

**物理端到端是最有说服力的一个数，也最难造假**：
拍「手划过画面中线」和「舵机转过中线」，数中间隔了几帧，每帧 4.17 ms。

> 数字小一点完全不影响，**口径不清才是硬伤**。
