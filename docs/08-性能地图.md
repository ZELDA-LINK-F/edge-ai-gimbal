## 0 · 三条铁律（先记住这些，再看数字）

### ① 全 GPU > 全 CPU > **混合（最差）**

Q4 模型三种分层的实测：

| 配置 | 生成速度 | 说明 |
|---|---|---|
| **全 GPU**（28/28 层） | **29.0 tok/s** ⚡ | 最快 |
| 全 CPU（0/28 层） | 17.3 tok/s | 竟然不慢 |
| **混合**（26/28 层，出厂默认） | **16.2 tok/s** 😑 | **最慢** |

**原因**：混合模式下每生成一个 token 都要在 CPU↔GPU 之间搬运数据，同步开销吃掉收益。
⇒ **要么全给 GPU，要么全给 CPU，别"各一半"。**

### ② 真正该盯的是「提示处理」，不是生成速度

```
提示处理耗时（同样 38 token 的提示）：
   全 CPU：1434 ms
   全 GPU： 104 ms      ← 快 14 倍
```

生成速度只差 1.8 倍，**提示处理差 14 倍**。
短提示看不出来；一旦 RAG 往提示里塞几块资料（上千 token），差距会被放大成"能不能用"。

### ③ 8GB 上没有"同时"，只有"轮流"

实测：qwen-fast 占着 2.1GB 时，再加载 Q8 模型 → **直接失败**：

```
error loading model: unable to allocate CUDA0 buffer
```

即使 free 显示还有 3.1GB 可用 —— 因为 **CUDA 需要连续物理内存块**，碎片化就分配不出来。

**正确姿势**：换模型前先执行 `ollama stop <旧模型>`。

| qwen2.5:1.5b-instruct | **Q8_0** | 1.6 GB | 28（全GPU） | ❌ **加载失败** | — | — | 内存不够 |
| qwen2.5:1.5b-instruct | Q8_0 | 1.6 GB | 20 | ❌ **加载失败** | — | — | 内存不够 |
| qwen2.5:1.5b-instruct | Q8_0 | 1.6 GB | 12 | 2.8 GB | 11.7 tok/s | 92 ms | 能跑但慢（40% 溢出 CPU） |

**⚠️ 为什么出厂默认是 26 层而不是 28？**

查前人笔记（坑 #1）：**全 GPU 时模型会偶发崩溃**（NaN logits → SIGABRT），降到 26 层后稳定（复现器 12/12 崩 → 0/12）。
⇒ **这个 26 是一个"稳定性补丁"，不是性能调优。** 想换 28 层前，先接受"可能偶发崩溃"的风险。

## 3.5 · ⚠️ 内存碎片：最容易被忽略的坑

**现象**：反复加载/卸载模型后，即使 `free` 显示还有 3~5G 可用，加载模型仍报
`unable to allocate CUDA0 buffer`。

**原因**：CUDA 需要**连续的物理内存块**。长时间运行后内存池碎片化，大块分配失败。

**诊断指标**：tegrastats 里的 `lfb`（最大连续空闲块）
```
清理前：lfb 2x4MB      可用 3.2G
清理后：lfb 152x4MB    可用 5.0G     ← 一条命令救回来
```

**解法**
```bash
sudo sysctl vm.drop_caches=3     # 释放页缓存（首选，秒级生效）
ollama stop <旧模型>             # 换模型前先卸载
# 还不行 → 重启板子（最彻底）
```

## 6 · 阶段 B 小结

**在 8GB 的统一内存上，一切性能问题最后都归结为一句话：**

> **速度 × 内存 × 稳定性 —— 三者只能取其二。**

- 想快 → 全 GPU，但内存多花 0.8G，且可能触发崩溃
- 想省内存 → 全 CPU，但长提示要等 1.4 秒
- 想稳 → 用出厂的 26 层，接受只有一半速度

## 7 · 8GB 内存管理策略（Playbook）

### 7.1 先认清约束（这是设计约束，不是 bug）

| 约束 | 含义 |
|---|---|
| **统一内存** | 7.62G 由 CPU/GPU **共享**，没有独立显存 |
| **CUDA 要连续物理块** | 内存碎片会导致"**假性 OOM**"（看着够、就是分配不出来） |
| 内存不可扩展 | 不像 PC 能加内存条 |
| 功耗极低（空闲 5.3W） | 可以 24 小时常开，这是它的优势 |

### 7.2 预算分层：谁可以动

| 层 | 典型占用 | 策略 |
|---|---|---|
| 系统基础 | ~1.0 G | ❌ 不可动 |
| 桌面 GUI | ~450 M | ✅ **最大单笔收益**（远程开发就关掉） |
| 常驻服务 | 判难度器 147M / Open WebUI 362M / jupyter 49M / docker 60M | ⚖️ 按"用不用得上"取舍 |
| **模型（按需）** | 1.1 ~ 3.2 G | 🔄 **一次只留一个** |
| 计算余量 | 剩余 | ⚠️ 至少留 500M~1G |

**额度公式**：`能给模型的内存 ≈ available − 500M（安全余量）`

### 7.3 六条原则

1. **大块优先** —— 全 GPU 或全 CPU，**别混合**（混合最慢，实测 16.2 vs 29.0 tok/s）
2. **分时而非并行** —— 8GB 上"同时"是奢侈品，一次只驻留一个模型
3. **量化优先** —— **Q4 是这台机器的甜点**；Q8 内存翻倍且可能直接装不下
4. **碎片要回收** —— drop_caches 先试，还不行就重启
5. **常驻要算账** —— 常驻 = 用内存换延迟（判难度器 147M 换掉 330ms 重载，值）
6. **算不到就外包** —— 本地+云端路由 = **架构级省内存**

### 7.4 工具箱（八种手段）

| 手段 | 做法 | 省下 | 代价 |
|---|---|---|---|
| 关桌面 GUI | systemctl set-default multi-user.target | ~450 M | 没图形界面 |
| 释放页缓存 | sysctl vm.drop_caches=3 | 整理碎片（lfb 8M→608M） | 无（缓存会重建） |
| 卸载模型 | ollama stop 模型名 | 1~3 G | 下次重载 3~10s |
| 降分层 | num_gpu 调小 | 0.8~1 G | 速度变慢 |
| 缩上下文 | num_ctx 调小 | 线性节省 KV 缓存 | 能塞的资料变少 |
| 降量化 | Q8 → Q4 | 权重 ~50% | 精度略降 |
| 缩小图片 | 缩到 1024 宽以内 | 视觉 token | 细节变少 |
| 分时加载 | 用完就卸 | 全部 | 切换有延迟 |

### 7.5 遇事怎么办（决策树）

```
模型跑不起来
   │
   ├─ ① free -h 看 available
   │     └─ 不够 → 关非必需品（桌面 GUI / Open WebUI / jupyter）
   │
   ├─ ② 明明够却失败 → tegrastats 看 lfb（碎片）
   │     └─ sysctl vm.drop_caches=3 → 还不行就重启
   │
   ├─ ③ 还不行 → 降配置：num_gpu ↓ → num_ctx ↓ → 量化精度 ↓ → 换更小模型
   │
   └─ ④ 还不行 → 换架构：分时加载 / 本地+云端路由
```

|---|---|---|---|---|---|
| 纯文本对话 | qwen-fast，num_gpu 26 | 2.1 G | ~4.5 G | 3.1 G | ✅ |
| RAG 长提示 | qwen-fast，全 GPU | 1.9 G | ~4.3 G | 3.3 G | ✅ |

### 7.7 前辈的架构本身就是一套内存管理方案

| 他们的设计 | 省下了什么 |
|---|---|
| 判难度器**常驻**（147M） | 避免每次重载编码器（1.8G / 330ms） |
| 闲聊走本地小模型 | 避免为一句"你好"动用大模型 |
| **ASR 空闲 900s 自退** | 用完把 3 GB 还给系统 |
| RAG 只取 **top-3** | 限制提示长度 = 限制 KV 缓存 |
| 复杂问题才走云端 | 根本不在本地占内存 |

**这五条，每一条都是"内存换体验"的具体决策 —— 这才是边缘 AI 的工程能力。**

### 7.8 心法

> **内存管理的本质不是"优化"，是"取舍"。**
> **速度 × 内存 × 稳定性 —— 三者只能取其二。**
